## 4. 執行一致性離線最小驗證（`v71_exec_check.py`，結果 `exec_check.json`）
做法：另寫一個只依交易所規則記帳的模型（每個 positionSide 一個合併部位、平均成本法、全倉錢包、指定數量市價與止損、減倉不得超量），把 V70 引擎的 1,133 筆成交當訂單重播，逐小時比對保證金餘額。

| 檢查 | 結果 |
|---|---|
| 逐小時保證金餘額與引擎權益的差額 | 等於引擎累計成本（期末 3,173.349U，完全一致），全程單調不減 |
| 被拒訂單（減倉超過合併部位） | 0 |
| 期末部位 | 多空皆 0 |
| 同一小時同方向兩腿都有成交 | 3 個小時，依固定順序處理後無衝突 |
| ① 同向合併後，指定數量止損只平現行腿 | 通過（1.7 → 剩 0.5） |
| ② 現行實盤的 closePosition 止損 | 會把趨勢腿一起平掉，證明不能沿用 |
| ③ 全部平倉後合併已實現＝分腿帳本 | 通過 |
| ④ 部分減倉的數量與已實現 | 通過 |
| ⑤ 減倉量超過部位會被拒 | 通過 |
| ⑥ 全倉強平條件（保證金餘額 ≤ 維持保證金） | 通過；V70 全期小時內保守權益最低仍為總維持保證金的 110 倍，名目對權益最高 1.8 倍 |

**缺少的實盤功能**（要做整套一致性稽核前必須先有）：
1. 指定數量的 STOP_MARKET 止損（現在是 closePosition）。
2. 兩腿的虛擬子帳本與數量歸屬（現在 executor 每個方向只認一筆）。
3. 趨勢腿的日線訊號、每日再平衡與部分加減倉。
4. 依錢包餘額計算名目的固定風險下單（現在是固定保證金或 GK 分組倍數）與以參考帳本計的熔斷。
5. 全倉模式與 5 倍槓桿的設定與啟動檢查（現在逐倉 20 倍，程式不設定保證金模式）。
6. 重啟後的兩腿狀態還原、合併部位與交易所對帳、同秒多筆訂單的先後與部分成交處理。
未驗證：止損實際成交價、標記價與最新價觸發差異、交易所維持保證金級距。

## 7. 結論與下一步
1. V70 的首筆是可重現的啟動行為，但 2021 年初 5 個啟動日的第一年要靠它才為正。啟動日敏感度顯示趨勢腿在多數啟動日都優於對照，集中度檢查則不過，V70 延伸不具前瞻資格。
2. 連敗長度在統計上就是勝率與筆數的結果，沒有可辨識的聚集。本輪沒有找到能把勝率提高到 62% 以上的規則。可以確定做到的只有降低連敗金額（固定風險下單與低波動暫停）。
3. 目前沒有資料足夠、機制不同且尚未測過的連敗方向可以直接接續；若要再試，需要一個能大幅提高單筆勝率的新機制，而不是連敗狀態規則。
